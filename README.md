# spring-gift

- ☑️ 패키지 구조 변경하기
- ☑️ 테스트 코드 작성하기
- ☑️ 분석 과정에서 발생한 문제 해결
  - ☑️ 주문 생성 시, 트랜잭션 처리
  - ☑️ 컨트롤러에 비즈니스 로직 제거
  - ☑️ wish 테이블 유니크 제약 추가
  - ☑️ 재고 음수 가능성 방지하기

---

## AI 활용 기록

**도구**: Claude Code (claude-sonnet-4-6)

### 활용 방식

**계획 먼저, 구현 나중**
구현 전 항상 계획을 먼저 검토하고 승인 후 진행했다. PLAN.md를 기준점으로 삼아 완료 항목을 지속적으로 업데이트했다.

**테스트와 리팩토링 분리**
테스트 작성과 구조 변경을 항상 별개 요청으로 분리했다. AI가 요청 범위를 벗어나 추가 개선을 하려 하면 명시적으로 제한했다.
```
"AdminProductController 테스트 코드 작성해줘 — 개선은 따로하지말고"
→ 테스트 확인 후 → "비즈니스 로직 서비스로 분리하자"
```

**이해 기반 검증**
AI 출력을 그대로 수용하지 않고 "왜?", "완전 정리 됐어?" 같은 질문으로 빠진 부분을 직접 확인했다. 이 과정에서 Spring이 `OptimisticLockException`을 `ObjectOptimisticLockingFailureException`으로 래핑한다는 점 등을 발견해 핸들러를 보완했다.

**결정은 직접, ADR로 문서화**
기술 선택지가 있을 때 AI에게 트레이드오프를 물어보되, 최종 결정은 직접 내렸다. 결정 근거는 ADR-008 ~ ADR-011에 문서화했다.
```
"낙관적 락 vs 비관적 락 어떤 게 나으려나"
→ 트레이드오프 확인 → "ADR로 추가하고 @Version 추가해보자"
```

### 주요 수정 내용

| 작업 | 방법 |
|---|---|
| 서비스 계층 분리 (Category, AdminMember, AdminProduct) | 테스트 먼저 작성 → 리팩토링 |
| 낙관적 락 (`@Version`) | ADR-011 작성 → 구현 → 통합 테스트로 동작 검증 |
| wish 유니크 제약 | DB 마이그레이션만 추가 (엔티티 어노테이션은 Flyway 환경에서 불필요하다고 판단) |
| Entity `@Column`/`@Table` 명시 | SQL 스키마와 직접 비교하며 작성 |
