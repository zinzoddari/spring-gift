기존 프로젝트를 리팩토링하는 과제였기에, API 스펙을 변경하지 않고 로직 개선하는데에 집중 하였습니다.

---

## AI 사용 방식

**도구**: Claude Code (claude-sonnet-4-6)

### 활용 방식

- 구현 전 항상 계획을 먼저 검토하고 승인하여 진행하였습니다. 작업은 `PLAN.md`를 기준점으로 관리 해 주었습니다.
- 항상 작은 단위로 작업을 하려고 노력했습니다.
  - 먼저 테스트 코드를 작성하고, 테스트가 통과하는지 확인 후 비즈니스 로직을 개선하는 방식으로 진행했습니다.
```
"AdminProductController 테스트 코드 작성해줘 — 개선은 따로하지말고"
→ 테스트 확인 후
→ "비즈니스 로직 서비스로 분리하자"
```
- AI 결과를 무조건 수용하지 않고, 의도치 않은 변경이 있으면 직접 감지해서 되돌렸습니다. 
  - 예를 들어 AI가 `edit.html`의 비밀번호 필드를 무단으로 제거하거나, 린터가 코드를 되돌리는 상황을 직접 확인하고 재요청했습니다.
  - "왜 이런 결과가 나온 것인지에 대한 근거를 알려줘" 같은 질문으로 빠진 부분을 계속 확인했습니다.
- 기술적으로 고민이 되는 부분은 AI에게 선택지와 트레이드오프를 ADR로 정리하게 하고, 최종 결정은 직접 내렸습니다. 

```
"낙관적 락 vs 비관적 락 어떤 게 나으려나"
→ 트레이드오프 확인
→ "ADR로 추가하고 @Version 추가해보자"  ← 결정은 직접
```

### 반복적으로 사용한 패턴

```
# 테스트 → 리팩토링 분리 패턴
"[컴포넌트] 테스트 코드 작성해줘"  →  테스트 통과 확인  →  "[컴포넌트] 서비스로 분리하자"

# 결정 문서화 패턴
"[기술 고민] ADR로 추가하고 [결정]해보자"

# 검증 패턴
직접 코드를 확인하고 누락된 부분이 있으면 재 요청 →  빠진 케이스 추가 확인
```

### 문서 구조

| 파일 | 용도 |
|------|------|
| `PLAN.md` | 작업 목록 관리. 진행 중 / 완료 항목을 체크리스트로 추적하여 AI와 작업 범위를 공유하는 기준점으로 활용 |
| `docs/ai-log.md` | AI와 함께 수행한 작업 이력. 날짜별로 요청 내용, 결과, 근거를 기록하여 작업 흐름을 추적 |
| `docs/adr/` | 기술적 의사결정 기록(ADR). 패키지 구조, 클라이언트 추상화, 인증 방식 등 고민이 필요했던 결정을 선택지·트레이드오프·결론 형식으로 문서화 |
