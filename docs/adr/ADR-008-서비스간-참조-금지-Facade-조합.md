# ADR-008: 서비스 간 직접 참조 금지 — Facade로 조합

## 날짜
2026-05-24

## 상태
`결정됨`

---

## 상황

`OptionService`가 옵션 로직을 처리하면서 상품 존재 여부 확인을 위해 `ProductRepository`를 직접 주입받고 있다.
이를 `ProductService`로 교체하면 서비스가 다른 서비스를 직접 참조하는 구조가 되어,
의존 방향이 불명확해지고 순환 의존 위험이 생긴다.

---

## 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. Service → Service 직접 참조 | 구현 간단, 클래스 수 적음 | 순환 의존 위험, 도메인 경계 불명확, 서비스 단위 테스트 복잡 |
| B. Facade로 조합 (Service → Service 금지) | 각 서비스가 단일 도메인만 책임, 의존 방향 단순화, 독립 테스트 용이 | 클래스 수 증가, 단순 조합에도 Facade 파일 필요 |

---

## 결정

> **B를 선택한다. 서비스는 다른 서비스를 직접 참조하지 않는다.**

이유: 서비스가 서비스를 참조하면 의존 그래프가 복잡해지고 순환 의존 위험이 생긴다.
여러 서비스를 조합해야 할 때는 Facade를 두어 Controller → Facade → Service 방향을 일관되게 유지한다.

---

## 트레이드오프

감수하는 것: 도메인 간 조합이 필요할 때마다 Facade 파일이 추가됨  
얻는 것: 서비스 단일 책임 유지, 순환 의존 원천 차단, 서비스 단독 단위 테스트 단순화

---

## 결과

- 의존 방향: `Controller → Facade → Service → Repository`
- 서비스는 자기 도메인의 Repository만 주입받는다
- 도메인 간 조합이 필요한 경우 Facade를 생성한다 (`KakaoAuthFacade`, `OptionFacade` 등)
- Facade는 트랜잭션 경계를 소유하고, 하위 서비스 메서드는 해당 트랜잭션에 참여한다
