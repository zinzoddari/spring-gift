# ADR-011: 재고 동시성 제어 — 낙관적 락 (@Version)

## 날짜
2026-05-24

## 상태
`결정됨`

---

## 상황

`Option.subtractQuantity()`는 단일 요청에서는 음수 재고를 방지하지만, 동시 요청이 들어올 경우
두 트랜잭션이 같은 재고 값을 읽고 모두 체크를 통과한 뒤 차감하면 실제 재고보다 더 많이 팔릴 수 있다.
재고 정합성을 보장하기 위해 동시성 제어 방식을 선택해야 한다.

---

## 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. 낙관적 락 (`@Version`) | 충돌이 드문 경우 DB 락 없이 성능 유지, 구현 단순 | 충돌 시 `OptimisticLockException` 발생, 호출 측 재시도 필요 |
| B. 비관적 락 (`PESSIMISTIC_WRITE`) | 충돌 자체를 차단, 재시도 불필요 | 조회 시점에 행 잠금 — 트래픽이 몰리면 대기·타임아웃 위험 |
| C. 아무것도 하지 않음 | 코드 변경 없음 | 동시 주문 시 재고 음수 가능, 정합성 보장 불가 |

---

## 결정

> **A를 선택한다. `@Version`으로 낙관적 락을 적용한다.**

이유: 같은 옵션에 동시 주문이 몰리는 경우는 드물어 충돌 빈도가 낮다.
비관적 락은 행 잠금 유지 시간만큼 DB 커넥션이 점유되어 트래픽 집중 시 병목이 되므로,
충돌 시 예외로 감지하고 호출 측에서 처리하는 낙관적 락이 더 적합하다.

---

## 트레이드오프

감수하는 것: 충돌 시 `OptimisticLockException` 발생 — 클라이언트에 재시도 또는 "잠시 후 다시 시도" 안내 필요  
얻는 것: 정상 흐름에서 DB 락 없이 성능 유지, 재고 음수 불가 보장

---

## 결과

- `Option` 엔티티에 `@Version private Long version` 필드 추가
- 동시에 같은 옵션에 두 주문이 들어오면 한 쪽은 `OptimisticLockException` 발생
- `GlobalExceptionHandler`에서 `OptimisticLockException`을 409 Conflict로 처리
