# ADR-007: 상품명 유효성 검증 방식

## 날짜
2026-05-23

## 상태
`제안됨`

---

## 상황

현재 상품명 검증은 `ProductNameValidator`(순수 Java 유틸 클래스)가 담당하고, 컨트롤러의 `validateName()`이 이를 명시적으로 호출해 `IllegalArgumentException`을 던지는 방식이다.
검증 규칙이 세 가지(길이 제한, 허용 특수 문자, "카카오" 포함 여부)이며, "카카오" 규칙은 `allowKakao` 파라미터로 컨텍스트에 따라 달라진다.
Spring Bean Validation(`@Valid` + `ConstraintValidator`)으로 전환할지 유지할지 결정이 필요하다.

---

## 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. Spring Bean Validation (`@Valid` + `ConstraintValidator`) | 표준 방식, `@NotBlank`·`@Positive` 등 기존 제약과 일관, 컨트롤러 코드 단순화(`validateName()` 제거), `BindingResult`로 필드별 에러 분리 가능 | `allowKakao` 같은 컨텍스트 의존 규칙을 어노테이션으로 표현하기 어려움, `ConstraintValidator` 빈 등록 필요, 규칙별 어노테이션이 늘어나면 보일러플레이트 증가 |
| B. 현행 유지 (`ProductNameValidator` 유틸 클래스) | 순수 Java로 테스트 용이, 컨텍스트(allowKakao) 전달이 자연스럽고 유연, 로직이 한 곳에 집중 | 컨트롤러·서비스에서 명시적 호출 필요, Spring 검증 파이프라인과 분리되어 일관성 저하, 실수로 호출 누락 가능 |

---

## 결정

> **미결정 — 추가 검토 필요**

`allowKakao`처럼 호출 컨텍스트에 따라 규칙이 달라지는 검증은 Bean Validation 어노테이션으로 표현하기 어렵다.
단기적으로는 B안을 유지하되, 검증 호출을 컨트롤러가 아닌 서비스 계층으로 이동해 누락 위험을 줄이는 것을 권장한다.
`allowKakao` 로직이 정리되거나 컨텍스트 의존성이 사라지면 A안 전환을 재검토한다.

---

## 트레이드오프

감수하는 것: Spring 검증 파이프라인과의 불일치, 호출 누락 위험  
얻는 것: 컨텍스트 의존 규칙(`allowKakao`)을 자연스럽게 처리, 순수 Java로 테스트 용이

---

## 결과

- 단기: `validateName()` 호출을 서비스 계층으로 이동 (컨트롤러에서 제거)
- 장기: `allowKakao` 요구사항이 정리되면 `@ValidProductName` 커스텀 어노테이션으로 전환 검토
