# ADR-009: 주문 카카오 알림 — 트랜잭션 커밋 후 처리

## 날짜
2026-05-24

## 상태
`결정됨`

---

## 상황

`OrderFacade`에서 주문 생성 흐름(재고 차감 → 포인트 차감 → 주문 저장)을 하나의 `@Transactional`로 묶을 때,
카카오 알림 전송이 트랜잭션 안에서 호출되면 두 가지 문제가 생긴다.

1. DB 커넥션이 외부 HTTP 호출 시간만큼 점유됨
2. 카카오 호출은 실패해도 주문에 영향을 줘선 안 되지만, 논리적으로 트랜잭션 범위 안에 포함된 것처럼 보임

---

## 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. try-catch로 삼키기 (현행) | 코드 단순 | 커밋 전 HTTP 호출, 커넥션 점유, 롤백 시에도 알림 시도됨 |
| B. `TransactionSynchronizationManager.afterCommit()` | 커밋 후 실행 보장, 이벤트 구조 불필요, Facade 한 곳에서 관리 | 동기 호출이므로 여전히 응답 지연 가능 (단, 커밋 후라 커넥션은 반납됨) |
| C. `@TransactionalEventListener` | 가장 느슨한 결합, 비동기 확장 용이 | 이벤트 클래스·퍼블리셔 추가 필요, 현재 규모 대비 과도한 구조 |

---

## 결정

> **B를 선택한다. `afterCommit()` 콜백으로 트랜잭션 커밋 후 카카오 알림을 실행한다.**

이유: 커밋이 성공한 경우에만 알림이 시도되고, DB 커넥션은 커밋 시점에 반납된다.
이벤트 기반(C안)은 향후 비동기 처리가 필요할 때 전환하면 충분하고, 현 단계에서는 Facade 내부에서 처리하는 것이 단순하다.

---

## 트레이드오프

감수하는 것: 카카오 HTTP 호출이 동기로 일어나 응답 지연 가능 (단, 커밋 후라 트랜잭션에 무관)  
얻는 것: 롤백 시 알림 미전송 보장, 커밋 전 커넥션 점유 해소, 구조 단순 유지

---

## 결과

- `OrderFacade.createOrder()`는 `@Transactional`을 유지하고, 카카오 알림만 `afterCommit()` 콜백 안으로 이동
- 알림 실패는 기존과 동일하게 try-catch로 삼킴 (best-effort)
- 향후 알림 지연/재시도가 필요해지면 C안(`@TransactionalEventListener` + 비동기)으로 교체
