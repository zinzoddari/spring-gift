# ADR-009: 주문 카카오 알림 — 트랜잭션 커밋 후 처리

## 날짜
2026-05-24

## 상태
`수정됨` (최초 결정: B안 → 변경: C안)

---

## 상황

`OrderFacade`에서 주문 생성 흐름(재고 차감 → 포인트 차감 → 주문 저장)을 하나의 `@Transactional`로 묶을 때,
카카오 알림 전송이 트랜잭션 안에서 호출되면 두 가지 문제가 생긴다.

1. DB 커넥션이 외부 HTTP 호출 시간만큼 점유됨
2. 카카오 호출은 실패해도 주문에 영향을 줘선 안 되지만, 논리적으로 트랜잭션 범위 안에 포함된 것처럼 보임

---

## 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. try-catch로 삼키기 (현행) | 코드 단순 | 커밋 전 HTTP 호출, 커넥션 점유, 롤백 시에도 알림 시도됨 |
| B. `TransactionSynchronizationManager.afterCommit()` | 커밋 후 실행 보장, 이벤트 구조 불필요, Facade 한 곳에서 관리 | 동기 호출이므로 여전히 응답 지연 가능 (단, 커밋 후라 커넥션은 반납됨) |
| C. `@TransactionalEventListener` | 가장 느슨한 결합, 비동기 확장 용이 | 이벤트 클래스·퍼블리셔 추가 필요, 현재 규모 대비 과도한 구조 |

---

## 최초 결정 (B안)

최초에는 B안을 선택했다. 이벤트 구조 없이 Facade 한 곳에서 처리할 수 있어 단순하고,
커밋 후 실행이 보장되어 롤백 시 알림 미전송도 보장된다는 이유였다.

---

## 결정 변경 이유 (B → C)

B안을 실제로 구현하려 할 때 단위 테스트 문제가 드러났다.

`TransactionSynchronizationManager.registerSynchronization()`은 활성 트랜잭션이 없으면
`IllegalStateException`을 던진다. 단위 테스트(`@ExtendWith(MockitoExtension.class)`)에서는
실제 트랜잭션이 없기 때문에, 테스트마다 `TransactionSynchronizationManager.initSynchronization()`
초기화 및 수동으로 `afterCommit()` 콜백을 발동시키는 boilerplate가 필요해진다.

이 비용이 이벤트 클래스 하나를 추가하는 비용보다 크다고 판단하여 C안으로 변경한다.

---

## 결정

> **C를 선택한다. `@TransactionalEventListener`로 트랜잭션 커밋 후 카카오 알림을 실행한다.**

이유: 커밋 후 실행 보장은 B안과 동일하면서, 단위 테스트에서 이벤트 발행 여부만 검증하면 되어
테스트 구조가 자연스럽다. 향후 비동기 처리(`@Async`)로의 전환도 애노테이션 하나로 가능하다.

---

## 트레이드오프

감수하는 것: 이벤트 클래스(`OrderCreatedEvent`)와 리스너 클래스 추가  
얻는 것: 롤백 시 알림 미전송 보장, 커밋 전 커넥션 점유 해소, 테스트 용이성, 비동기 전환 용이

---

## 결과

- `OrderFacade.createOrder()`는 주문 저장 후 `OrderCreatedEvent`를 발행
- 별도 리스너(`KakaoNotificationListener`)가 `@TransactionalEventListener`로 커밋 후 알림 처리
- 알림 실패는 기존과 동일하게 try-catch로 삼킴 (best-effort)
- 향후 비동기가 필요해지면 리스너에 `@Async`만 추가
